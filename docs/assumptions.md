# Assumptions

## Varun

- **T00 Python environment:** torch / open_clip_torch / geopandas / rasterio wheels aren't published for Python 3.14 yet (the system default here), so `environment.yml` targets Python 3.12. A local venv at `bkk-flood-poc/.venv` (Python 3.12) is used instead of conda (conda isn't installed in this environment); exact resolved versions are frozen in `requirements-lock.txt`.
- **T70 real bug found and fixed: TimeSlider animation keyed on object identity, not content.** The play/pause interval's `useEffect` depended on the `manifest` object itself; any re-fetch that resolved to an equivalent-but-different object reference (confirmed: React StrictMode's deliberate double mount on page load causes exactly this) tore down and restarted the interval, which could eat enough of a short playback window to look like animation never advanced. Fixed by depending on `manifest?.n_frames` (a primitive) instead.
- **T70 headless-Chromium rendering jank, not a bug:** while chasing the above, traced the *actual* per-tick timing under Playwright and found the first tick after `playing` turns on can be delayed ~1.4s past its nominal 500ms interval (then the timer always catches up and settles into the correct cadence). This reproduces with `--disable-background-timer-throttling` too, so it isn't Chrome's background-tab timer clamp — it lines up with the first real map repaint (new BitmapLayer texture + 4 preloaded frame fetches) competing for the main thread under headless software-rendered WebGL. Not an app bug; `tests/time_slider.spec.ts` now polls for the first tick (up to 8s) instead of asserting a fixed-wall-clock number of ticks in a short window. A real user's GPU-accelerated, focused tab shouldn't see this.
- **T70 MetricsPanel POC targets (§21) are a guess:** the parent requirements doc with the real POC pass/fail thresholds isn't in this repo (same gap noted for T01/T53). Picked reasonable-looking targets (wet RMSE ≤0.15 m, CSI@0.10 ≥0.5, |peak timing error| ≤30 min, |volume error| ≤20%, B1 comparison ≥0.7, coverage@95 ≥0.9) tuned so the T01 fixture's MOCK_metrics.json values all pass — revisit once §21 is available.
- **T70 validation `points` (hit/miss) has no backend data yet:** `GET /api/validation/{run_id}` has always returned an empty `points` FeatureCollection (T30); computing real hit/miss points needs joining scenario observations against model depth, which isn't in T70's file list (`dashboard/render/render_error.py`, `frameLayer.ts`, `MetricsPanel.tsx`, `OodBanner.tsx`). Built `validationPointsLayer` to render a `hit: boolean` property convention so it's ready the moment the backend populates it, rather than guessing a schema it doesn't need yet.
- **T70 "compare vs surrogate" reuses `compareSource` as a toggle:** the store already had an unused `compareSource: string | null` field; repurposed it (`null` = off, `'surrogate'` = swipe mode comparing the current hydraulic run against the scenario's surrogate run) rather than adding a new boolean field, since no other meaning for it existed yet.
- **T70 swipe divider is a linear lon-interpolated slider, not a real screen-space drag:** `SwipeDivider` maps a 0–100% range input linearly across the domain's longitude span rather than using MapLibre's own screen↔lnglat projection (which `MapView` doesn't expose to parent components). The domain here is ~0.1° wide, so projection distortion across it is negligible for a POC swipe control.
- **T01 bug found by T41, fixed:** `make_depth_nc`/`make_surrogate_nc` set the netCDF `scenario_id` attr to the bare `SCENARIO_ID` constant (`"BKK-S99"`) instead of the `MOCK_`-prefixed id everything else in the fixtures uses (`scenario.yaml`'s `scenario_id`, the `run_id` attr itself, the observations directory name). Harmless until something filtered runs by scenario_id — `GET /api/runs?scenario_id=MOCK_BKK-S99` (T30) silently returned `[]` because of it, which T41's App.tsx (which does exactly that filter, unlike T30's own tests) surfaced immediately in a live browser. Fixed at the source in `tools/fixtures/make_fixtures.py`; regenerate fixtures+frames to pick it up. Nothing in the T00–T54 test suites caught this because none of them join on scenario_id across artifacts — worth remembering: schema-level tests (does this file have the right shape) don't catch cross-artifact consistency bugs (do two files agree on the same id).
- **T01 depth.nc rise/recede shape:** amplitude(t) is a triangular pulse (linear rise to 0.8 m at t=40, linear recede to 0 by t=95) — the card only pins the peak value/index, not the curve shape.
- **T01 pond footprint cutoff:** values are hard-zeroed below a Gaussian density of 1e-2 so "zero elsewhere" is exact, not just small.
- **T01 GeoJSON `is_mock` placement:** T11 asks for "`is_mock: true` in the FeatureCollection metadata" but GeoJSON has no standard metadata key. Fixtures set it under a `metadata` object at the FeatureCollection root *and* on every feature's `properties`, since the real consumer (store.py, not yet built) isn't known to prefer one location.
- **T01 citizen_reports.geojson schema:** SCENARIO_SCHEMA.md isn't in this repo, so the field list (`report_id, ts_utc, depth_cm, description, source_ref, data_class`) mirrors `road_flood_points.geojson`'s contract rather than a confirmed spec.
- **T01 scenario.yaml `categories`:** set to `["pluvial"]` — the category taxonomy isn't defined anywhere available in this repo.
- **T01 MOCK_metrics.json keys:** `wet_rmse_m, csi_0.10, peak_timing_error_min, volume_error_pct, b1_comparison, coverage_95` — reconstructed from the metric names referenced in VARUN_IMPLEMENTATION.md's T70 MetricsPanel spec, not from §17.10 itself (that parent doc isn't in the repo).
- **T40 `sigma_v1` / `error_v1` colormap hexes:** the card only says "light → dark purple" (sigma) and "diverging, red = over, blue = under" (error) without pinning exact colors. Used ColorBrewer's sequential Purples (sigma) and Reds/Blues (error) step palettes. If T70/the dashboard need pixel-perfect legend colors later, revisit `dashboard/render/colormaps.py`.
- **T30 `/api/runs/{run_id}/satellite` shape:** the card says the response is "`[{...}]` or `[]` + gap", which isn't valid as a single JSON value (an array can't carry a sibling field). Implemented as `{"items": [...], "gap": str|None}` consistently; no consumer exists yet (T31/T60 not built) to conflict with this choice.
- **T53 `synth_obs.py` cell lookup (superseded by T54, not yet swapped in):** `synth_obs.py` still uses its own plain nearest-grid-cell lookup rather than the now-built `validation.cctv.cam_cells`/`compare.model_series`. Harmless since it's pipeline-testing-only (never metrics), but worth switching over next time `synth_obs.py` is touched, to drop the duplicate logic.
- **T51 rain-rate oversampling:** the card wants frames oversampled from hours when a nearby gauge recorded "≥ 10 mm/h", but `stations.timeseries` values here are per-15-min totals (mm per interval), not a rate. Approximated the hourly rate as `value * 4`. Revisit once real DDS/TMD gauge data (T21) lands with a known unit convention.
- **T71 "Mahalanobis"/OOD heuristic:** no real training-distribution covariance exists to compute an actual Mahalanobis distance against, so `mock_infer._edge_distance` is a Euclidean norm over each param normalized to [-1,1] by its sampler range. OOD threshold (1.5, out of a max possible ~2.236) is a judgement call tuned so a single near-edge param doesn't trip it but several at once does — revisit once a real surrogate exists.
- **T71 version-before-caching:** the cache key (`run_id`) includes `surrogate_version`, which we only learn by actually calling `predict()`. Mock mode's version is a fixed constant so this costs nothing; if/when `surrogate.infer.predict` (HU6) lands and is expensive even to probe, this may need a cheaper way to get the version first.
- **T71 WhatIfPanel.tsx:** built as part of T31 once the React app existed to put it in — see T31's entry below for what that involved.
- **T71 transient HDF5 stderr noise under rapid concurrent calls:** firing several `/api/predict` calls back-to-back with no delay sometimes prints an HDF5 "unable to determine if file is accessible" diagnostic to stderr for a background render. It's cosmetic only — xarray's engine fallback absorbs it internally, every job still reaches `DONE` with no error, and it didn't reproduce under the test suite's normal (non-hammering) call pattern. Not worth chasing further for a POC demo path that doesn't fire requests with zero gap between them.
- **T51 double-labelling isn't automatically coordinated:** "already-labelled sha1" is skipped *per labeller* (not globally), so a second labeller can still see and label frames the first one already did — but there's no mechanism that hands labeller B the exact same 50 frames labeller A did for κ. In practice, coordinate that manually (e.g. labeller B works through the same cameras/time range first).
- **T54 road_clip is always false:** no OSM roads file exists yet at `data/raw/osm/roads.geojson` (Dhanya's handoff). `cam_cells.py` already has the real intersect-with-roads code path; it just falls back to the plain 30 m buffer (`road_clip: false`) until that file lands.
- **T53 `depth_proxy_bin` formatting:** the card's only example is `"0.15-0.30"`; for `SEVERE_FLOODING` (open-ended upper bound `null`), formatted as `"0.30-"` rather than inventing an upper number.
- **T50 fixture images aren't photorealistic:** the T01 synthetic CCTV frames are a solid blue rectangle for "water", and that rectangle's size depends only on `frame_idx`/`is_wet` — not `cam_id` — so many frames across different cameras are byte-identical (frames dedup by sha1 to 30 unique images out of 300 rows, which is correct/intended embedding-cache behavior, not a bug). CLIP's zero-shot flood probability on these synthetic images stays near-zero for every class regardless of the "water" rectangle, so the card's soft wet-vs-dry check (§6 T50 Verify) warns rather than failing — expected until real CCTV frames are captured (T20) or `is_mock` metrics are validated against T52's labelled data.
- **T31 Carto Positron basemap now needs the GL vector style, not the classic raster XYZ URL:** the card says "raster ... no key", but `basemaps.cartocdn.com/light_all/{z}/{x}/{y}.png` now returns keyless requests watermarked "API KEY REQUIRED" (verified directly via curl with browser-like headers, not assumed — a CARTO policy change since this plan was written). Their GL vector style (`basemaps.cartocdn.com/gl/positron-gl-style/style.json`) remains genuinely free/keyless and is the officially documented way to use Positron with MapLibre today; `MapView.tsx` uses that instead.
- **T31 real bugs found and fixed while verifying the map (not visible from code review alone — needed an actual running browser to surface):**
  1. `.map-container`'s CSS (`position: absolute; inset: 0`) was silently overridden by maplibre-gl's own injected stylesheet (`.maplibregl-map { position: relative }`), since MapLibre adds that class directly onto the container element we hand it and both are single-class selectors of equal specificity — whichever stylesheet loads last in the bundle wins. Collapsed the map to 0 height. Fixed with an inline style (always wins regardless of cascade order).
  2. maplibre-gl's internal Web Worker failed to load under Vite dev's esbuild pre-bundling ("Worker failed to load"). Fixed with maplibre-gl's own documented Vite workaround: `optimizeDeps: { exclude: ['maplibre-gl'] }`.
  3. deck.gl's `MapboxOverlay` with `interleaved: true` shares maplibre's WebGL context/draw calls; when its render hook threw (`Cannot read properties of undefined (reading '_nearZ'/'height')`, from calling `map.addControl(overlay)` before the map's `'load'` event), it sometimes corrupted shared GL state badly enough that maplibre's *own* tile layer intermittently stopped repainting too — not just a dropped deck.gl frame, a blank map. None of this app's layers (a line outline, two point layers, a flat bitmap) need true 3D interleaving with map geometry, so switched to `interleaved: false` (deck.gl draws on its own separate canvas) *and* kept gating `addControl` on `'load'`. Both together were needed: `interleaved:false` alone still broke maplibre's own style pipeline (only `style.json` ever got fetched, never the sprite/tiles/fonts it references) when the control was added synchronously before `'load'`.
  4. The domain-boundary `GeoJsonLayer`'s stroke was pure white (`[255,255,255,220]`) — invisible against the Positron basemap's own near-white background. Confirmed the layer itself was rendering correctly (temporarily set it to solid red to verify) before concluding it was a contrast choice, not a bug, and repainted it dark slate instead.

  All four needed a live browser render to catch — the code looked correct, built cleanly, and passed `tsc`/lint throughout. Worth remembering next time something "looks right in code" for a mapping/WebGL stack: render it and watch the console.
